# Pairing Admin Frontend Guide

Pairing 관리자 프론트엔드의 코드 작성, 보안, 권한, API 연동 및 검증 기준입니다.

## 1. 현재 기술 스택

`package.json`을 최종 기준으로 삼습니다.

| 구분 | 현재 기술 |
| --- | --- |
| Framework | Next.js App Router 16.3.0 |
| UI Library | React 19.2.8 |
| Language | TypeScript 5 |
| Styling | Tailwind CSS 4 |
| Package Manager | npm |
| Lint | ESLint 9 |
| Unit / E2E Test | 미도입 |

새로운 라이브러리나 상태 관리 도구는 팀 합의 없이 추가하지 않습니다.

## 2. 폴더 구조

기능이 추가될 때 아래 구조를 기준으로 검토하되, 폴더를 미리 만들지 않고 실제로 필요한 것만 추가합니다.

```text
src/
├─ app/                 # 페이지, 레이아웃, 라우팅
├─ features/            # auth, members 등 관리자 도메인별 기능
├─ components/ui/       # 여러 도메인이 공유하는 UI
├─ hooks/               # 여러 도메인이 공유하는 훅
├─ lib/                 # API 클라이언트, 인증 등 인프라
├─ services/            # 여러 도메인이 공유하는 API 호출
├─ types/               # 프로젝트 전역 타입
└─ utils/               # 프로젝트 전역 순수 함수
```

도메인 후보에는 인증, 회원, 프로젝트, 계약, 결제, 정산, 리뷰, 신고, AI Agent가 있습니다. 실제 제품 범위와 API가 확정된 도메인만 구현합니다.

## 3. 코드 작성

### TypeScript

- 변경되지 않는 값에는 `const`를 사용하고 `var`는 사용하지 않습니다.
- `any`를 피하고 API 요청·응답, 컴포넌트 Props 타입을 명시합니다.
- enum, union, nullable 여부는 실제 API 계약을 기준으로 합니다.

### React와 Next.js

- 함수형 컴포넌트를 사용합니다.
- 서버 컴포넌트를 기본으로 검토합니다.
- 상태, Effect, 이벤트, 브라우저 API가 필요할 때만 `"use client"`를 사용합니다.
- 불필요한 상태와 Effect를 만들지 않습니다.
- 책임이 커진 컴포넌트는 기능 단위로 분리하고 중복 로직은 훅이나 공통 함수로 추출합니다.
- 현재 Next.js 버전의 동작은 `node_modules/next/dist/docs/`에 설치된 문서를 확인합니다.

### 네이밍

| 대상 | 규칙 | 예시 |
| --- | --- | --- |
| 컴포넌트와 파일 | PascalCase | `MemberTable.tsx` |
| 함수와 변수 | camelCase | `getMemberList` |
| 훅 | `use` 접두사 | `useMemberFilters` |
| 타입 | PascalCase | `MemberListResponse` |
| 상수 | UPPER_SNAKE_CASE | `DEFAULT_PAGE_SIZE` |

## 4. 관리자 보안과 권한

- 화면에서 요소를 숨기는 것만으로 권한을 보장하지 않습니다. 관리자 API도 백엔드 권한 검사를 전제로 합니다.
- 관리자 역할과 권한명을 추측하지 않습니다.
- 비로그인(401)과 권한 부족(403)을 구분합니다.
- Access Token과 Refresh Token을 `localStorage`에 저장하지 않습니다.
- 비밀번호, 쿠키, 세션, 토큰, API key 및 요청 body 전체를 로그에 출력하지 않습니다.
- 실제 사용자 개인정보를 테스트 데이터로 사용하지 않고, 화면과 Issue/PR 스크린샷에는 필요한 정보만 노출합니다.
- 권한 확인 중에는 보호된 화면을 먼저 렌더링하지 않습니다.
- 사용자 조회 실패, 네트워크 오류, 서버 오류를 무조건 401 또는 403으로 처리하지 않습니다.
- 인증 쿠키나 토큰 전달 방식은 백엔드 계약 없이 변경하지 않습니다.

## 5. 위험 작업

회원 정지·탈퇴, 관리자 권한 변경, 프로젝트 강제 종료, 계약 취소, 결제 취소·환불, 정산 승인·취소, 리뷰·신고 삭제, AI Agent 활성화·비활성화는 위험 작업으로 취급합니다.

위험 작업에는 다음을 적용합니다.

- 실행 전 확인 모달과 명확한 대상 정보
- 중복 클릭 방지와 처리 중 버튼 비활성화
- 성공·실패 결과 안내
- 처리 완료 후 데이터 재조회
- 백엔드 감사 로그 정책 확인

삭제, 환불, 권한 변경에는 낙관적 업데이트를 기본으로 사용하지 않습니다.

## 6. API 연동

연동 전에 URL, HTTP method, path/query parameter, request/response body, nullable 필드, enum, 페이지네이션, 정렬·검색 조건, 인증, HTTP status와 `errorCode`를 확인합니다.

실제 계약을 확인하지 못한 mock을 실제 API 계약처럼 작성하지 않습니다.

목록 화면은 로딩, 성공, 빈 결과, 검색 결과 없음, 실패, 재시도, 페이지네이션과 필터 초기화를 구분합니다. 변경 API는 확인, 중복 제출 방지, 처리 중, 성공·실패 및 처리 후 재조회를 다룹니다.

## 7. 관리자 UI와 접근성

- 표, 검색, 필터, 페이지네이션은 기존 공통 컴포넌트를 우선합니다.
- 위험 작업은 일반 작업과 시각적으로 구분합니다.
- 상태는 색상뿐 아니라 텍스트로도 전달합니다.
- 긴 이름, 이메일, 회사명, 프로젝트명이 레이아웃을 깨뜨리지 않게 처리합니다.
- 빈 상태와 오류 상태를 구분합니다.
- 키보드 focus, input-label 연결, 버튼의 접근 가능한 이름을 확인합니다.
- Modal은 ESC, focus trap, 닫기 동작을 확인합니다.

## 8. 검증

현재 사용할 수 있는 명령은 다음과 같습니다.

```bash
npm run lint
npm run build
```

테스트 도구와 테스트 스크립트는 아직 없습니다. 존재하지 않는 `npm run test`를 실행하거나 통과했다고 기록하지 않습니다.

| 변경 유형 | 최소 검증 |
| --- | --- |
| 문서 | 링크, 경로, 오탈자, 민감 정보 |
| UI | lint + 브라우저 확인 |
| 공통 컴포넌트 | lint + 사용하는 주요 화면 |
| 라우팅 | lint + build + 직접 URL 접근 |
| API | lint + 실제 요청·응답 + 실패 처리 |
| 인증 | 401, 403, 세션 만료 |
| 위험 작업 | 성공, 실패, 중복 실행 방지 |
| 배포 전 | lint + build + 주요 관리자 흐름 |

실행하지 않은 검증을 통과로 기록하지 않습니다.
