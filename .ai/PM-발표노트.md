# PM 발표 준비 러닝 노트

> 이 문서는 완성된 발표 대본이 아니라, 개발 과정에서 발표에 쓸 근거와 사례를 계속 모으는 재료 창고입니다.
> 확인된 사실만 적고, 기억에 의존하거나 팀 확인이 필요한 내용은 반드시 `❓ 확인 필요`로 표시합니다.

## 사용법

- 개발 중 의미 있는 결정·변경·문제가 생기면 해당 항목에 2~5줄로 기록합니다.
- 가능한 경우 날짜, 담당자, 회의록·이슈·PR·커밋·화면 캡처 등 근거를 함께 남깁니다.
- 기능 목록보다 **왜 결정했는지**, **무엇이 바뀌었는지**, **결과가 어땠는지**를 우선 기록합니다.
- 발표 직전에는 `🎤 발표 후보`만 추려 PPT와 발표 대본으로 옮깁니다.

### 태그

- `🎤 발표 후보`: 발표에서 직접 설명할 만한 핵심 내용
- `📌 참고`: 발표 질문 대응이나 보충 설명에 쓸 내용
- `❓ 확인 필요`: 팀원·문서·데이터로 사실 확인이 필요한 내용
- `🧾 근거`: 회의록, 문서, 이슈, PR, 커밋, 캡처, 수치 등의 위치

## 3. 문제를 직면하고 해결한 경험

> 발표용으로는 문제를 많이 나열하지 말고, 근거가 충분한 2~3개를 골라 깊게 설명합니다.

### 사례 작성 틀

#### 사례 A — 회원관리 API 계약 확인과 배포 요청 경로 수정

- `상황`: 2026-08-13 관리자 회원관리 화면의 더미 데이터를 실제 백엔드 API로 전환했다.
- `문제`: 최초 전달 문서는 상세 응답만 설명해 목록·통계·상태 변경 계약을 확정할 수 없었고, 연동 후 브라우저가 `localhost:8081`로 직접 요청하면 배포 환경에서 연결이 거부되는 문제가 있었다.
- `원인`: 화면에 필요한 API 계약 문서가 분리되어 있었고, Next.js 코드가 실행되는 위치(브라우저 CSR와 Node.js SSR)에 따라 `localhost`의 대상이 달라지는 점이 Base URL에 반영되지 않았다.
- `선택지`: 확인되지 않은 목록 응답을 추측해 구현하거나 전체 가이드를 요청하는 방법, API 요청을 SSR로 옮기거나 브라우저 동일 출처 프록시를 사용하는 방법을 검토했다.
- `결정`: 전체 회원관리 가이드를 확인한 뒤 계약대로 구현하고, CSR 특성을 유지하면서 `NEXT_PUBLIC_API_URL`에 지정된 백엔드 도메인을 직접 호출하도록 최종 결정했다. 중간에 동일 출처 프록시 방식을 검토·적용했지만 실제 배포 구성과 달라 정정했다.
- `실행`: FE는 요약·목록·상세·정지·해제 연동, 검색·필터·페이지네이션과 예외 처리를 구현했다. BE 측 배포 환경에는 Nginx `/api` 프록시가 필요하다. 실제 담당자별 실행 여부는 `❓ 확인 필요`다.
